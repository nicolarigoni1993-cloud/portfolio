## Channel 3 — Public proof

Preferred proof hierarchy:
1. Live client work
2. Public-safe case studies
3. Technical screenshots with no sensitive data
4. GitHub public repositories
5. Engineering notes
6. Product demos when ready

Avoid:
- inflated metrics
- fake client logos
- vague "AI-powered" claims
- exposing unreleased private products just to fill content

---

## Lead flow

1. Client discovers Nicola or Ninth Slate
2. Client describes problem
3. Qualify scope
4. Choose service package
5. Define expected result
6. Agree milestone
7. Implement
8. Verify
9. Deliver
10. Ask for review/testimonial only after successful outcome

---

## Qualification questions

- What is currently happening?
- What should happen instead?
- Can the issue be reproduced?
- Which stack is involved?
- Is there an existing repository?
- Is there a staging/test environment?
- Are there deadlines?
- What must not change?
- What does "done" mean?

---

## Initial offer priority

The first paid wins should favor:
- focused bugs
- small features
- responsive fixes
- API integration
- Supabase/PostgreSQL work
- FastAPI backend work
- QA/release hardening

Reason:
These are easier to scope, verify and review than large greenfield builds.
